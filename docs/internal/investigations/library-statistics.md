# Investigation — Titan Library Statistics

**الحالة:** مكتملة — القرار المعماري اتُّخذ — 2026-07-24

**القرار:** **Adapt** — تحتاج Titan إلى طريقة موثوقة لشرح هويتها وبنيتها
وتاريخها، لكن ليس إلى نظام إحصاءات runtime أو جامع metrics داخل المكتبة.

---

## 1. السؤال الحقيقي

اقتراح "إحصاءات Titan" يبدو بسيطاً، لكنه يخلط ثلاثة أسئلة مختلفة:

1. **ما هي Titan؟** — حزمة، عقد، أسطح API، توافق، وبنية.
2. **من يستخدم Titan؟** — تنزيلات، مشاريع معتمدة، مجتمع، وإشارات تبنٍ خارجية.
3. **كيف تتطور Titan؟** — مساهمون، قرارات، تحقيقات، صيانة، وتاريخ.

هذه ليست بيانات من المصدر نفسه، ولا يملك المستهلك نفسه الصلاحية نفسها عليها.
إذا جُمعت في `stats()` واحدة، ستبدو الأرقام متساوية في الأهمية بينما هي ليست
كذلك. الهدف الصحيح ليس عرض أكبر عدد من الأرقام، بل أن يفهم القارئ Titan بشكل
أدق بعد رؤيتها.

---

## 2. ما تملكه Titan حالياً

Titan تملك بالفعل عدة أسطح متخصصة، وكل سطح يجيب عن سؤال مختلف:

| السطح | السؤال الذي يجيب عنه |
|---|---|
| `bot.inspect()` | ماذا سُجّل في هذا البوت؟ |
| `bot.health()` | هل بنية هذا البوت مكتملة وسليمة؟ |
| `bot.lint()` | هل تصميم هذا البوت يحترم اتفاقيات Titan؟ |
| `titan.profiler` | كم يستغرق تنفيذ update في بيئة محكومة؟ |
| `titan.timeline` | ما القرارات المعمارية التي شكّلت Titan؟ |
| `titan.atlas` | لماذا صُممت Titan بهذه الطريقة؟ |
| `The Titan Ledger` | من ترك أثراً دائماً في بناء المشروع؟ |
| `CHANGELOG.md` | ماذا تغير بين الإصدارات؟ |

إضافة سطح عام باسم `stats` ستحتاج إلى تبرير السؤال الجديد الذي تجيب عنه.
لا يجوز أن تكون مجرد تجميع لما تفعله هذه الأسطح بالفعل.

هناك أيضاً مصدران موثوقان لحقائق المكتبة:

- `pyproject.toml` لاسم التوزيعة، الإصدار، Python المدعوم، والتبعيات.
- `CONTRACT.md` والوثائق وADRs للسطح العام والسلوك والبنية المقصودة.

هذه المصادر أفضل من نسخ قيم مشتقة إلى كائن runtime قد ينفصل عنها.

### 3.1 إحصاءات المكتبة

المشاريع الكبيرة تعرض غالباً:

- رقم الإصدار وPython المدعوم.
- إصدار البروتوكول أو API الخارجي المدعوم.
- حالة الاختبارات والتوثيق أحياناً عبر badges.
- روابط release notes والتغيير.
- قائمة features مكتوبة، لا مجرد عدد modules.

هذه المعلومات مفيدة لأنها تساعد المطور على اتخاذ قرار: هل الإصدار مناسب
لبيئته؟ ما الذي يدعمه؟ أين يقرأ التغييرات؟ الأرقام هنا مختصرة ومسنودة بمصدر
واضح.

لكن حتى في هذه المشاريع لا تُعامل كل الأرقام كحقيقة معمارية. عدد النجوم أو
التنزيلات يظهر عادة كإشارة خارجية في README أو PyPI، لا كجزء من API التشغيلية
للمكتبة.

### 3.2 إحصاءات الاستخدام والمجتمع

PTB وaiogram وPyTelegramBotAPI تستخدم badges وروابط إلى PyPI والمجتمعات وقنوات
الدعم. هذا مناسب للمشاريع واسعة الاستخدام، لكنه لا يعني أن الرقم جزء من
المكتبة نفسها.

وثائق Python Packaging تذكر أن PyPI لا يعرض تنزيلات الحزم مباشرةً لأسباب منها
التخزين المؤقت وتغير البيانات المستمر. وتحليل التنزيلات ممكن عبر dataset عام،
لكن تفسير الرقم يحتاج فترة زمنية ومصدر البيانات وفهم التنزيلات الآلية.

النتيجة:

- download count ليس عدد مستخدمين.
- download count ليس عدد bots.
- stars أو watchers ليست adoption.
- GitHub dependents لا تمثل كل المستهلكين ولا تضمن أنهم ما زالوا نشطين.
- عضوية قناة أو مجموعة لا تقيس الاستخدام الفعلي.

XGBoost يقدم مثالاً مختلفاً ومفيداً: سجل المساهمين يذكر الأثر النوعي لبعض
المساهمين، ولا يحوّل البشر إلى ترتيب رقمي. وDjango يشرح أن المساهمة تشمل
الكود والمساعدة والتوثيق والمجتمع، لا commits فقط. هذا أقرب إلى فلسفة Titan من
لوحة ترتيب.

## 4. تحليل الفئات الثلاث

### 4.1 Library Statistics — ما يستحق أن يكون عاماً

#### مفيد ومناسب للنشر

- اسم التوزيعة واسم الاستيراد.
- الإصدار الحالي ومكان release history.
- إصدارات Python المدعومة.
- الاعتماديات الأساسية، عند الحاجة لفهم متطلبات التشغيل.
- الأسطح الرسمية: Core، `titan.playground`، `titan.profiler`،
  `titan.timeline`، `titan.atlas` وغيرها.
- مبادئ التشغيل: async، polling، contract-first، stability-driven.
- خريطة الوثائق: API، concepts، ADRs، migration، recipes.
- رابط العقد العام ومكان قراءة القرارات.

هذه حقائق وصفية أو metadata مستقرة، وليست metrics تتطلب جمعاً مستمراً.

#### مفيد لكن يجب عرضه بحذر

- عدد قرارات ADR.
- عدد domains أو public exports.
- عدد الاختبارات.
- تاريخ آخر إصدار.

يمكن أن تساعد هذه القيم كـ snapshot مؤرخ، لكن لا ينبغي أن تصبح هوية المشروع أو
أن تُكرر في عدة ملفات. الأعداد المشتقة عرضة للتقادم، وقد تدفع إلى تحسين الرقم
بدلاً من تحسين النظام.

#### لا يضيف فهماً حقيقياً

- عدد الأسطر أو الملفات.
- عدد classes أو functions الداخلية.
- حجم wheel كعنوان مستقل.
- عدد commits.
- عدد الخصائص لمجرد أنه عدد.
- ترتيب Titan مقابل مكتبات أخرى.

### 4.2 Ecosystem / Usage Statistics — ما لا تستطيع Titan ادعاءه

لا توجد في المستودع الحالي قناة موثوقة تقيس bots أو التطبيقات المبنية على
Titan. لذلك لا يجوز إنشاء قيمة أو عرض تقدير لهذه الأرقام.

إذا احتاج maintainer لاحقاً إلى متابعة adoption، فالمكان الصحيح هو أدوات
المستودع أو مصدر PyPI خارجي، مع:

- رابط المصدر.
- الفترة الزمنية.
- تعريف metric.
- توضيح أنها إشارة adoption وليست عدد مستخدمين.
- عدم وضعها في runtime أو في عقد المكتبة.

ما يبقى عاماً في Titan اليوم هو رابط خارجي اختياري، لا API ولا رقم مخزّن في
الحزمة.

### 4.3 Project & Maintainer Statistics — التاريخ لا المنافسة

القيمة الحقيقية هنا نوعية:

- المساهمون وأثرهم في [The Titan Ledger](../../../CONTRIBUTORS.md).
- القرارات والتحقيقات في `docs/decisions/` و`docs/internal/investigations/`.
- التغيرات المعلنة في `CHANGELOG.md`.
- قواعد المشروع في `CONTRACT.md` و`docs/architecture/`.
- خط التطور الزمني في `titan.timeline`.
- نشاط الصيانة، إذا عُرض، كفترة وتاريخ لا كحكم على الأشخاص.

يجب أن يبقى هذا السطح:

- غير تنافسي.
- غير مرتب للأفراد حسب عدد commits.
- خالياً من البريد الإلكتروني والبيانات الشخصية.
- منفصلاً عن بيانات مستخدمي bots.
- صريحاً في التفريق بين "قرار معماري" و"مؤشر نشاط".

## 5. أين تعيش القدرة؟

### أ. CLI command

**القرار: Reject في الوقت الحالي.**

CLI باسم مثل `titan stats` سيحتاج entry point وسلوكاً جديداً، مع أن المستخدم
الذي يريد تشغيل بوت لا يحتاج إحصاءات عن المكتبة. كما أنه سيغري بإضافة مصادر
شبكية متغيرة أو تقارير طويلة إلى أداة يفترض أن تكون محلية وحتمية.

قد يصبح CLI مناسباً لاحقاً إذا ظهر workflow حقيقي مثل فحص توافق مشروع قبل
الإصدار. لا يوجد هذا الضغط الآن.

### ب. Public Python API

**القرار: Reject في v1 من هذه الفكرة.**

`from titan import stats` أو `from titan.stats import ...` سيحوّل حقائق
مشتقة من metadata والوثائق إلى contract جديد. سيحتاج المستهلكون إلى توقع
استقرار حقول مثل `api_surface` و`architecture_size`، مع أن هذه الحقول قابلة
للتغير وغير ضرورية لتنفيذ bot.

لا ينبغي أن تستخدم API العامة شبكة أو GitHub أو PyPI لجلب أرقام خارجية. ولا
ينبغي أن تكرر `health` أو `inspect` أو `profiler`.

إذا ظهر مستهلك آلي حقيقي لاحقاً، يمكن دراسة `titan.about` كواجهة صغيرة
للحقائق الثابتة فقط، لا `titan.stats` لقياسات متغيرة. هذا ليس قرار تنفيذ الآن.

### ج. Documentation output

**القرار: Adopt.**

هذا هو المكان الطبيعي للمرحلة الأولى: ملف بشري القراءة باسم مثل
`docs/project-profile.md` أو قسم واضح في README، يشرح:

1. هوية الحزمة وإصدارها وتوافقها.
2. الأسطح الرسمية وخريطة الوثائق.
3. مبادئ البنية وما الذي لا تدعيه Titan.
4. تاريخ القرارات والمساهمين.
5. روابط خارجية اختيارية لإشارات PyPI أو GitHub مع حدود تفسيرها.

يجب أن يكون هذا الملف مصدر عرض لا مصدراً جديداً للحقيقة. لا يعيد نسخ كل
أرقام metadata، ولا يحاول أن يتحدث تلقائياً من شبكة خارجية.

### د. Companion bot integration

**القرار: خارج النطاق.**

البوت المرافق تطبيق رسمي مستقبلي للنظام البيئي لـ Titan، وليس واجهة إحصاءات.
تقييمه كتطبيق نظام بيئي مستقل خارج نطاق هذا التحقيق ويستحق دراسة معمارية
منفصلة. لا تُعدّ هذه الدراسة مرجعاً لتصميمه.

ما تثبته هذه الدراسة في حدود نطاقها:

- الإحصاءات لا يجب أن تستلزم وجود البوت المرافق أو تعتمد عليه.
- الإحصاءات لا يجب أن تعتمد على خدمات شبكية خارجية أثناء runtime.

**ملاحظة معمارية:** يُتوقع أن يكون البوت المرافق مستقبلاً أحد المستهلكين
الرسميين لـ Project Profile، وللإشعارات بالإصدارات، ولخدمات النظام البيئي
الأخرى. هذا دور طبيعي له بوصفه تطبيق النظام البيئي الرسمي، لا دليل على أن
الإحصاءات تستدعي وجوده.

### هـ. Release information system

**القرار: Adapt.**

الإصدارات موجودة بالفعل في `pyproject.toml` و`CHANGELOG.md`، ومصدر Titan
الرسمي هو مستودع GitHub. التحسين الصحيح مستقبلاً هو اتساق هذه المصادر وربطها،
لا إنشاء نظام إحصاءات موازٍ. أي generation آلي يجب أن يبدأ فقط بعد ظهور مشكلة
drift حقيقية.

## 6. ما يجب أن يبقى خاصاً أو خارج المكتبة

لا يجوز أن تعرض قدرة Titan أو تخزن:

- tokens أو أسرار أو بيانات اعتماد.
- email أو PII للمساهمين دون موافقة صريحة.
- chat IDs أو user IDs أو محتوى رسائل bots.
- أسماء bots أو مشاريع تعتمد على Titan دون إعلان موثوق وموافقة مناسبة.
- metrics داخلية من بيئة maintainer كأنها facts عامة.
- تقديرات adoption مبنية على عينة صغيرة.
- telemetry صامتة أو اتصالات شبكية من import أو runtime.

حتى بيانات الصيانة العامة يجب أن تُقدم كسياق تاريخي، لا كترتيب إنتاجية أو
حكم على قيمة شخص.

## 7. القرار المعماري

**Adapt: Titan تحتاج "Project Profile" بوصفه مفهوماً، لا "Statistics Subsystem".**

### تعريف المفهوم

Project Profile مفهوم معماري، وليس نوع ملف. هو: عرض منظم وموثوق لهوية
Titan وبنيتها وتاريخها، مجمَّع حصراً من المصادر الرسمية ولا يملك بيانات
خاصة به.

التوثيق هو أول مستهلك (First Consumer) للمفهوم، لا التعريف نفسه. مستهلكون
آخرون يمكن أن يتحقق كل واحد منهم بشكل مستقل في وقته:

- التوثيق — المستهلك الأول والأبسط.
- واجهة برمجية صغيرة مثل `titan.about` — عند ظهور مستهلك آلي حقيقي.
- البوت المرافق — بوصفه مستهلكاً رسمياً للنظام البيئي.
- الموقع الرسمي أو IDE Plugin أو أي مستهلك رسمي آخر يُقرَّر لاحقاً.

إضافة مستهلك جديد في المستقبل لا تستدعي إعادة هذا التحقيق، لأن المفهوم
والمصادر ثابتان؛ ما يتغير هو طريقة العرض فحسب.

### القاعدة الذهبية: مصدر الحقيقة

**Project Profile لا يملك بياناته الخاصة.**

كل حقيقة يعرضها يجب أن تُستقى مباشرةً من مصدر رسمي موجود:

| البيانات | المصدر الرسمي |
|---|---|
| الاسم والإصدار وPython المدعوم | `pyproject.toml` |
| العقد والأسطح الرسمية | `CONTRACT.md` |
| القرارات المعمارية | `docs/decisions/` عبر `titan.timeline` |
| تاريخ التغييرات | `CHANGELOG.md` |
| المساهمون وأثرهم | `CONTRIBUTORS.md` (The Titan Ledger) |
| المبادئ والفلسفة | `docs/architecture/` و`titan.atlas` |

أي معلومة لا مصدر رسمي لها لا تدخل في Project Profile. هذه القاعدة تمنع نشوء
نسخ موازية تتباعد مع الوقت ثم يصبح "الإصدار الصحيح" مجهول المكان.

### المبادئ الناتجة

> **اعرض ما يشرح Titan، لا ما يمكن عده عنها.**

> **Project Profile يجمع، لا يختزن.**

وبالتالي:

- **Adopt:** مفهوم Project Profile مع قاعدة مصدر الحقيقة، والتوثيق أول تطبيق
  له.
- **Reject:** runtime `stats()`، network fetching داخل المكتبة، rankings،
  وvanity metrics.
- **Defer:** كل مستهلك إضافي — `titan.about` أو CLI أو غيرهما — إلى أن يظهر
  احتياج حقيقي لا يمكن خدمته بالمستهلك القائم.

## 8. الحد الأدنى الصحيح إذا بدأ التنفيذ لاحقاً

إذا ثبتت الحاجة بعد هذه الدراسة، فأول تطبيق للمفهوم يجب أن يكون:

1. مستهلكاً وثائقياً واحداً — التوثيق هو الشكل الأول والأبسط لـ Project
   Profile، لا تعريفه.
2. بلا تبعيات أو اتصالات خارجية.
3. بلا أرقام adoption غير قابلة للتحقق.
4. بمعلومات مستقاة حصراً من: `pyproject.toml`، `CONTRACT.md`، ADRs،
   `CHANGELOG.md`، و`The Titan Ledger` — لا مصدر آخر.
5. بعناوين ثابتة: Identity، Compatibility، Architecture، Public Surfaces،
   Project History، External Signals.
6. بروابط خارجية مؤرخة أو موصوفة، لا نسخ رقمية تُعامَل كحقائق محلية.
7. مع اختبار روابط أو فحص drift فقط إذا ظهر احتياج مستقل لذلك؛ لا نبني CI
   لمجرد وجود الفكرة.

لا ينبغي أن تحتوي النسخة الأولى على:

- `stats()` أو `report()` في الجذر.
- database أو cache.
- telemetry.
- dashboard.
- badge جديد بلا metric موثوق.
- قياس runtime، لأن هذا يخص `titan.profiler` عندما يكون مطلوباً.

## 9. الإجابات النهائية

### 1. هل تحتاج Titan إلى capability للإحصاءات؟

تحتاج Titan إلى **عرض منظم لهويتها وتاريخها**، لكنها لا تحتاج capability
runtime للإحصاءات في الوقت الحالي.

### 2. ما الفئات ذات القيمة؟

- حقائق المكتبة الثابتة: نعم، مستقاةً من مصادرها الرسمية في Project Profile.
- تاريخ المشروع والقرارات والمساهمون: نعم، بصياغة نوعية ومسنودة.
- الاستخدام الخارجي: فقط كمراجع اختيارية من مصادر موثوقة، لا كبيانات داخلية.

### 3. ما العام وما الخاص؟

العام: metadata المنشورة، العقد، الأسطح الرسمية، الإصدارات، القرارات،
والتاريخ العام للمساهمات — بشرط أن يكون لكل حقيقة مصدر رسمي واضح.

الخاص أو خارج المكتبة: أسرار، PII، بيانات bots، telemetry، وتقديرات adoption
غير القابلة للتحقق.

### 4. أين يعيش المفهوم؟ وأين يعيش أول مستهلك؟

**المفهوم** لا يقطن في مكان واحد — هو اتفاق على المصادر وقاعدة مصدر الحقيقة.
**المستهلك الأول** هو التوثيق. لا يعيش في Core أو `ctx`. مستهلكون لاحقون
— API آلية أو البوت المرافق أو غيرهما — تُدرس فقط عند ظهور احتياج حقيقي لا
يمكن خدمته بالمستهلك القائم. إضافة مستهلك جديد لا تغير المفهوم ولا تستدعي
إعادة هذا التحقيق.

### 5. ما الذي يجب تجنبه؟

الخلط بين المقاييس، vanity metrics، الأرقام بلا فترة أو مصدر، الشبكة أثناء
runtime، تكرار الأسطح القائمة، وترتيب الأشخاص أو المشاريع. والأخطر: السماح
لأي مستهلك باستيراد بياناته الخاصة خارج المصادر الرسمية، فهذا هو جذر التباعد
بين النسخ.

### 6. ما التطبيق الأول الصحيح؟

أول تطبيق لـ `Project Profile`: مستهلك وثائقي محلي، يجمع من المصادر الرسمية
فقط، يعرض المعنى قبل العدد، ويترك adoption لمصادره الخارجية. كل مستهلك لاحق
— برمجي أو عبر البوت المرافق — يطبّق نفس القاعدة الذهبية: يجمع من المصادر
ذاتها ولا يضيف مصدراً موازياً.

## 10. مراجع التحقيق

تمت مراجعة المصادر في 2026-07-24. الروابط أعلاه هي المراجع الأساسية؛ من
القرارات المهمة المستخلصة منها:

- PTB وaiogram وPyTelegramBotAPI تعرض الإصدار وPython المدعوم والميزات وروابط
  المجتمع غالباً عبر التوثيق وbadges، لا عبر API runtime للإحصاءات.
- PTB يوجه المساهم إلى issues والاختبارات والمجتمع، بدلاً من اختزال المشاركة
  إلى commit count.
- Django يشرح المساهمة كعمل كود وتوثيق ومساعدة ومجتمع.
- XGBoost يربط بعض المساهمين بأثر نوعي، لا بترتيب رقمي.
- Python Packaging تميز بين dataset تنزيلات مفيد للتحليل وبين رقم adoption
  بسيط مضلل في صفحة المشروع.
