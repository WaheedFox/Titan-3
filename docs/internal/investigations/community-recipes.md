# تحقيق — Community Recipe Ecosystem

**الحالة:** مفتوحة — في انتظار قرار معماري

> **سياسة التوزيع الحالية:** تُثبّت Titan Core من GitHub. إشارات PyPI في هذا
> التحقيق تخص حزم الوصفات المجتمعية المستقلة، لا حزمة Titan نفسها.

**تاريخ:** 2026-07-27
**الهدف:** تصميم نظام بيئي مجتمعي لـ Recipes حول Titan — ليس لشحن وصفات رسمية، بل لتعريف كيفية إنشاء وصفات خارجية ومشاركتها وتثبيتها وتوثيقها وصيانتها.

**الفلسفة المرجعية:** Termux — ليس نسخاً، بل استلهاماً. Titan يضع المعايير وقواعد البناء، المجتمع يبني المحتوى، لا registry مركزي ولا أدوات خاصة، الاتفاقيات هي البنية التحتية.

**ناتج هذا التحقيق:** وثيقة معيار — `ecosystem/recipes/STANDARD.md`

---

## 1. السؤال

Titan اليوم لديه `titan.recipes` — وصفات رسمية، مُختارة، مُجمَّدة بعد النشر، تعيش داخل المستودع الرئيسي، يصونها الفريق.

هذا النموذج لا يُفضي إلى نظام بيئي. الفريق يتحكم في القبول، وكل إضافة تصبح التزاماً دائماً.

السؤال: **كيف يمكن للمجتمع بناء وصفات Titan — خارج المستودع الرئيسي — دون كسر الحدود المعمارية التي يحكمها CONTRACT.md؟**

---

## 2. البنية الراهنة — المرجع للمقارنة

### ما يوجد الآن

```
src/titan/recipes/
├── __init__.py       ← يُصدّر الوصفات الرسمية فقط
└── welcome.py        ← الوصفة الوحيدة المنشورة
```

### قواعد الحد الموجودة في CONTRACT.md

الوصفة اليوم:
- كائن قابل للاستدعاء (`__call__`) يستقبل `Context`
- لا تُضيف حالة للبوت
- تستخدم Core APIs فقط: `@bot.on`، `ctx.*`، `bot.middleware()`، `bot.telegram.*`، النماذج الموجودة
- **محظور:** decorators جديدة، خصائص `ctx` جديدة، تسجيل middleware تلقائي، نماذج جديدة لغرض الوصفة فقط
- التأثير أُحادي الاتجاه: Core تُعرِّف، Recipes تستخدم

### الفجوة

كل هذا يصف الوصفات **الرسمية**. لا يوجد أي تعريف لما تعنيه وصفة **مجتمعية** — كيف تُسمَّى، كيف تُوزَّع، كيف تُعلن توافقها، كيف تتعامل مع إصدارات Titan المختلفة.

## 3. مراجعة النظم الخارجية — الأفكار المستخرجة فقط

الهدف من هذا القسم ليس الوصف، بل استخلاص الأفكار الهيكلية التي تنطبق على Titan.

---

### 3.1 Homebrew — الفكرة: Taps (مستودعات موازية)

**الفكرة التي تنطبق:** النظام البيئي لا يحتاج سجلاً مركزياً واحداً.

Homebrew يتيح "taps": مستودعات GitHub مستقلة تحتوي على formulae. المستخدم يُضيف tap بسطر واحد، ثم يُثبّت منه. لا توجد "موافقة" مركزية، ولا بنية تحتية مخصصة.

**ما يعنيه لـ Titan:** يمكن أن تكون وصفة مجتمعية حزمة Python عادية على PyPI. لا تحتاج Titan أن تصون سجلاً. التوزيع الموزّع هو الافتراض الصحيح لبيئة صغيرة.

---

### 3.2 npm / Cargo — الفكرة: اتفاقية التسمية بدلاً من السجل

**الفكرة التي تنطبق:** الاتفاقية تُنشئ نظاماً بيئياً قابلاً للاكتشاف بدون بنية تحتية.

في npm، حزم مثل `babel-plugin-*` أو `eslint-plugin-*` قابلة للبحث كنمط. في Cargo، نمط `diesel-*` يُشير لتوسعات قاعدة البيانات.

**ما يعنيه لـ Titan:** `titan-recipe-<name>` كاتفاقية تسمية للحزم على PyPI — بحث واحد يعطي كل الوصفات المتاحة. لا حاجة لأداة اكتشاف مخصصة.

---

### 3.3 npm — الفكرة: `peerDependencies`

**الفكرة التي تنطبق:** الحزمة تُعلن أنها تتطلب إصداراً محدداً من المضيف، لا أنها تُثبّته.

**ما يعنيه لـ Titan:** تسجل الوصفة نطاق التوافق المقصود في metadata،
وتستخدم مرجع GitHub لإصدار Titan Core الذي تستهدفه. لا يعتمد تثبيت Core
على وجود حزمة Titan في فهرس حزم.

---

### 3.4 VS Code Extensions — الفكرة: تعريف نقاط المساهمة

**الفكرة التي تنطبق:** الإضافة تُعلن ما تُقدمه، لا فقط ما تفعله.

كل إضافة VS Code لها manifest يُحدد: ما الأحداث التي تعالجها، ما الواجهات التي تضيفها. المستخدم يعرف ما يتوقعه قبل التثبيت.

**ما يعنيه لـ Titan:** ملف metadata للوصفة يتضمن: أي أحداث Titan تُعالجها، ما نوعها (handler, middleware-compatible, utility). يجعل الاكتشاف ممكناً آلياً مستقبلاً.

---

### 3.5 GitHub Templates — الفكرة: توزيع صفري البنية التحتية

**الفكرة التي تنطبق:** مستودع Template يكفي كنقطة بداية دون حزمة PyPI في بعض الحالات.

**ما يعنيه لـ Titan:** وصفة بسيطة جداً قد لا تستحق حزمة PyPI. مستودع GitHub بملف واحد كافٍ. الأنواع الأثقل (مكتبات كاملة) تحتاج PyPI.

---

### 3.6 Termux Packages — الفكرة: build scripts كتعريف

**ما يعنيه لـ Titan:** لا ينطبق مباشرةً. Titan recipes هي Python خالصة ولا تحتاج build scripts.

---

### خلاصة ما يُستخرج

| النظام | الفكرة | تنطبق؟ |
|---|---|---|
| Homebrew Taps | توزيع موزَّع بلا سجل مركزي | ✓ نعم — PyPI كافٍ |
| npm naming | اتفاقية تسمية تُنشئ قابلية الاكتشاف | ✓ نعم — `titan-recipe-*` |
| npm peerDeps | إعلان التوافق بشكل قياسي | ✓ نعم — `pyproject.toml` |
| VS Code manifests | تعريف نقاط المساهمة | ✓ جزئياً — مفيد للاكتشاف |
| GitHub Templates | توزيع صفري للوصفات البسيطة | ✓ اختياري |
| Cargo workspace | مجموعات من الحزم المترابطة | ✗ معقد لغير ضروري |
| Termux build scripts | تجميع باعتماديات نظام | ✗ لا ينطبق |

## 4. الإجابات المعمارية

---

### 4.1 ما هي وصفة Titan بالضبط؟

وصفة Titan هي **حزمة Python مستقلة** تُغلّف نمط معالجة شائعاً باستخدام Titan Core APIs حصراً، وتُقدمه للمطور في شكل كائن قابل للتهيئة والاستدعاء.

الوصفة لا تضيف سلوكاً للبوت ما لم يُسجّلها المطور بشكل صريح. في لحظة الاستيراد: لا شيء يحدث.

```python
# استيراد: لا شيء يحدث
from titan_recipe_spam import SpamFilter

# تهيئة: تضبط المعاملات فقط
spam = SpamFilter(sensitivity=0.8)

# تسجيل: المطور يقرر أين ومتى
@bot.on("message")
async def handle(ctx):
    await spam(ctx)
```

الفرق بين الوصفة الرسمية والمجتمعية:

| | رسمية | مجتمعية |
|---|---|---|
| مسار الاستيراد | `from titan.recipes import X` | `from titan_recipe_name import X` |
| الصيانة | فريق Titan | صاحب الحزمة |
| الاستقرار | مُجمَّد بعد النشر | semver |
| القبول | مراجعة داخلية | المجتمع |
| الموقع | `src/titan/recipes/` | حزمة PyPI منفصلة |

الوصفتان تتشاركان نفس القواعد المعمارية. الاختلاف في الملكية والتوزيع، لا في الهيكل.

---

### 4.2 ما الذي ينتمي داخل الوصفة؟

الوصفة حزمة Python كاملة تحتوي:

**الكود:**
- الكائن/الكائنات القابلة للاستدعاء (class أو function)
- دوال مساعدة داخلية (private) لا تُصدَّر للمطور مباشرةً
- type hints كاملة

**الوثائق:**
- `RECIPE.md` بهيكل موحَّد (مذكور في §4.9)

**الاختبارات:**
- اختبارات وحدة تعتمد على `MagicMock` للـ `Context` — لا تتطلب بوتاً حقيقياً
- اختبار واحد على الأقل للحالة الأساسية والحالة الاستثنائية

**Metadata:**
- `pyproject.toml` بالقسم `[tool.titan-recipe]` (مذكور في §4.8)

---

### 4.3 ما الذي لا ينتمي أبداً داخل الوصفة؟

هذه الحدود مشتقة مباشرةً من CONTRACT.md، موسَّعة لتشمل الحالة المجتمعية:

**محظور معمارياً — لا استثناءات:**
- تعديل `Context` بإضافة خصائص أو دوال جديدة
- إضافة decorators جديدة على `bot`
- تسجيل middleware تلقائياً عند الاستيراد
- إضافة نماذج جديدة (Models) تُعبّر عن مفاهيم Core
- الوصول المباشر إلى internals من Titan (أي شيء بشرطة سفلية `_x`)
- تصحيح (monkey-patching) لأي كلاس في `titan.*`

**محظور عملياً:**
- حالة تبقى بين الـ updates بدون إذن صريح من المطور (الوصفة لا تُنشئ storage تلقائياً)
- اعتماديات ثقيلة لا ضرورة معمارية لها (ML model في وصفة spam filter يُلزم المطور بـ torch)
- أي شيء يمنع البوت من العمل بدون الوصفة

**الاختبار العملي:** هل يعمل البوت بشكل طبيعي إذا حُذف استدعاء الوصفة من handler؟ إذا كانت الإجابة لا — الوصفة تجاوزت حدودها.

---

### 4.4 كيف تتكامل الوصفة مع مشروع Titan قائم؟

`pip install titan-recipe-<name>`، ثم استيراد وتسجيل.

لا scaffolding. لا تعديل على ملفات المشروع. لا `titan install`. لا إضافة entries لـ config files.

```python
# مشروع قائم — التغيير الوحيد هو هذا
from titan_recipe_antiflood import AntiFlood

flood = AntiFlood(limit=5, window=10)

@bot.on("message")
async def handle(ctx):
    if await flood.check(ctx):
        return
    # ... المنطق العادي
```

المشاريع القائمة تستفيد بنفس القدر من المشاريع الجديدة — لا فرق في طريقة الاستخدام.

**ماذا عن الوصفات التي تحتاج تهيئة عامة؟**

إذا كانت الوصفة تحتاج إعداداً مشتركاً بين handlers متعددة، الأسلوب الصحيح هو كائن واحد تُمرّره يدوياً، لا singleton يُسجَّل تلقائياً:

```python
# صحيح
flood = AntiFlood(limit=5, window=10)
# يُمرَّر صراحةً لكل handler يحتاجه

# خاطئ
AntiFlood.setup(bot, limit=5)  # تسجيل تلقائي — محظور
```

---

### 4.5 هل تُعدِّل الوصفات الملفات القائمة؟

**لا. بشكل مطلق.**

وصفة تُعدِّل ملفاً قائماً (سواء بـ CLI أو بكود) لا تُعدّ وصفة — تُعدّ أداة إعداد (scaffolding tool)، وهي نوع مختلف تماماً.

قاعدة الفحص: إذا استدعيت `uninstall` (حذفت الاستيراد وحذبت `pip`)، هل المشروع يعود لحالته تماماً؟ إذا لا — الوصفة علّمت أثراً دائماً في الكود.

---

### 4.6 كيف يُعلَن التوافق مع إصدارات Titan؟

على مستويين متكاملين:

**المستوى الأول — pip (إلزامي):**
```toml
# pyproject.toml للوصفة
[project]
dependencies = [
    "titan-framework @ git+https://github.com/WaheedFox/Titan.git@v1.0.0b1"
]
```
حدّث مرجع الوسم عند استهداف إصدار Titan مختلف؛ مصدر Core هو GitHub.

**المستوى الثاني — metadata قابل للقراءة (اختياري، لكن موصى به):**
```toml
# pyproject.toml للوصفة
[tool.titan-recipe]
titan-compatibility = ">=1.0,<2.0"
```

هذا القسم يتيح للأدوات المستقبلية (أو فحص يدوي) التحقق من التوافق بمعزل عن pip. قيمته الفورية هي إمكانية العرض في قائمة الوصفات المجتمعية ("يتوافق مع Titan 1.x").

**ماذا إذا تغيرت Core APIs؟**

Titan يتبع semver. تغيير يكسر CONTRACT.md = رفع major version. الوصفة تُعلن أقصى نسخة مقبولة، وتُحدَّث عند الحاجة. هذا نفس نهج كل مكتبة Python.

---

### 4.7 كيف تُوصف الاعتماديات؟

`pyproject.toml` القياسي بالكامل — لا حاجة لأي بنية خاصة.

```toml
[project]
name = "titan-recipe-antiflood"
version = "1.0.0"
dependencies = [
    "titan-framework @ git+https://github.com/WaheedFox/Titan.git@v1.0.0b1",
    # لا اعتماديات ثقيلة إذا أمكن
]
```

**مبدأ الاعتماديات الخفيفة:**

وصفة تتطلب قاعدة بيانات خارجية أو مكتبة ML كاعتمادية إلزامية تُلزم جميع مستخدمي Titan بتثبيتها. البديل: اعتماديات اختيارية (extras):

```toml
[project.optional-dependencies]
redis = ["redis>=4.0"]
```

ثم:
```python
# pyproject.toml
pip install titan-recipe-ratelimit[redis]
```

الوصفة تعمل مع fallback افتراضي (in-memory) بدون redis، وتُفعّل التخزين الدائم إذا كان redis متاحاً.

---

### 4.8 ما البيانات الوصفية (Metadata) التي يجب أن تحتويها كل وصفة؟

```toml
# pyproject.toml
[project]
name = "titan-recipe-<name>"           # اتفاقية التسمية إلزامية
version = "X.Y.Z"                      # semver إلزامي
description = "..."                    # جملة واحدة
license = {text = "MIT"}               # أو أي رخصة مفتوحة
dependencies = ["titan-framework @ git+https://github.com/WaheedFox/Titan.git@v1.0.0b1"]  # حدّث الوسم

[tool.titan-recipe]
titan-compatibility = ">=X.Y,<X+1.0"  # مرآة للـ dependency — قابل للقراءة البشرية
events = ["message", "new_member"]    # أحداث Titan التي تعالجها — للاكتشاف
recipe-type = "handler"               # handler | middleware-compatible | utility
```

**`recipe-type`** له ثلاث قيم:
- `handler` — مُصمَّمة للاستخدام داخل `@bot.on(...)` handler
- `middleware-compatible` — يمكن استخدامها كـ middleware عبر `bot.middleware()`
- `utility` — دوال مساعدة لا ترتبط بحدث محدد

**`events`** — قائمة الأحداث التي صُمِّمت الوصفة لها. `["*"]` إذا كانت عامة.

### 4.9 كيف تُوثَّق الوصفات؟

كل وصفة تحتوي ملف `RECIPE.md` بهيكل موحَّد مقتبس من نمط الوصفات الرسمية في Titan:

```markdown
# Recipe: <Name>

**Primary question this document answers: ...**

---

## The Pattern
[كود عامل كامل — أقصر مثال ممكن]

---

## What This Pattern Uses
[أي Core APIs تستخدمها الوصفة وسبب اختيار كل منها]

---

## Configuration
[جدول المعاملات إن وُجدت]

---

## When to Go Beyond the Recipe
[متى يُفضَّل كتابة الـ handler مباشرةً بدل استخدام الوصفة]

---

## Compatibility
[إصدارات Titan المدعومة]
```

**لماذا هذا الهيكل بالذات:**

يُجيب على السؤال الفعلي الذي جاء به المطور ("كيف أُرحّب بالأعضاء؟") قبل أن يُبيّن كيف يعمل الكود. هذا ما تفعله وثائق الوصفات الرسمية، والمجتمعية تتبع نفس المعيار.

### 4.10 كيف تختلف وصفات المجتمع عن مكوّنات Titan الرسمية؟

| الجانب | Titan الرسمي | مجتمعي |
|---|---|---|
| مسار الاستيراد | `titan.recipes.*` أو `titan.*` | `titan_recipe_<name>` |
| الاستقرار | مُجمَّد بعد النشر — لا كسر للعقود | semver — صاحب الحزمة يُقرر |
| المراجعة | الفريق الأساسي | المجتمع + issues عامة |
| الالتزامات | جزء من CONTRACT.md | لا |
| إعلان في الوثائق | `docs/recipes/` في المستودع | `RECIPE.md` في الحزمة + PyPI |
| التوزيع | جزء من حزمة `titan` | حزمة PyPI مستقلة |
| الضمان | تعمل مع كل إصدار معلن | تعمل ضمن نطاق التوافق المُعلَن |

**ما يبقى ثابتاً بين الاثنتين:**

القواعد المعمارية في CONTRACT.md (`titan.recipes — Official Patterns`) تنطبق على كليهما. وصفة مجتمعية تكسر الحد (تُضيف خاصية ctx، تُسجّل middleware تلقائياً) لا تُعدّ وصفة Titan — بغض النظر عن اسمها على PyPI.

Titan لا يملك آلية تطبيق تقني لهذا، ولا ينبغي له ذلك. الآلية: وثائق الحد الواضحة + مراجعة المجتمع.

## 5. ما لا تحتاجه Titan

هذه الأفكار قد تبدو منطقية لكنها تُضاف تكلفة دون مقابل حقيقي في هذه المرحلة:

**سجل مركزي مخصص:** PyPI + اتفاقية التسمية يوفران الاكتشاف. سجل مخصص يعني بنية تحتية يحتاج الفريق صيانتها.

**أداة CLI خاصة (`titan install recipe-x`):** `pip install titan-recipe-x` يفي بالغرض. أداة CLI تُضيف سطحاً للمشكلات دون قيمة إضافية.

**نظام plugin يحمّل الوصفات تلقائياً:** الوصفة المُحمَّلة تلقائياً تكسر مبدأ "لا شيء يحدث عند الاستيراد". المطور يُسجّل يدوياً — هذا ليس قصوراً، هو ضمان.

**مراجعة مركزية إلزامية للوصفات:** الوصفات الرسمية فقط تحتاج مراجعة الفريق. المجتمع يحكم على نفسه.

**إصدار "حزمة وصفات" رسمية:** `titan.recipes` يبقى صغيراً ومقيَّداً. تجميع وصفات مجتمعية في حزمة واحدة يضاد هدف "Titan framework، لا recipe collection".

## 6. ما تحتاجه Titan فعلاً

**فقط:**

1. **وثيقة معيار الوصفات المجتمعية** — تُعرّف الاتفاقية الكاملة: التسمية، الهيكل، metadata، الحدود، هيكل `RECIPE.md`. مستند واحد في `docs/`.

2. **تحديث CONTRACT.md** — قسم `titan.recipes` يُوسَّع بفقرة تُوضّح العلاقة مع الوصفات المجتمعية: نفس القواعد، مسار استيراد مختلف، لا ضمان من الفريق.

3. **مستودع مجتمعي (اختياري في المرحلة الأولى)** — ملف `README.md` في `titan-community/recipes` يسرد الوصفات المعروفة. بدون registry code، بدون automation. المجتمع يُعلن وصفاته بـ Pull Request.

هذا كل شيء. لا كود جديد في Core، لا بنية تحتية، لا تغيير على `titan.recipes` الحالية.

## 8. التوصية

**Accept** — مع نطاق محدد.

المعمارية واضحة وقابلة للتنفيذ بتكلفة منخفضة جداً. الحدود موجودة بالفعل في CONTRACT.md — ما ينقص هو تسمية المسار المجتمعي ووثيقة معيار واحدة.

**المشروط:**

- ADR يُعرِّف اتفاقية التسمية والـ metadata spec
- تحديث CONTRACT.md بفقرة تُوضّح العلاقة بالوصفات المجتمعية
- لا كود جديد في Core — كل شيء مشروح بالكامل
- المستودع المجتمعي اختياري في المرحلة الأولى — ينتظر حتى يوجد وصفتان أو ثلاث فعلياً

**ما هذه التوصية لا تعني:**

- تغيير `titan.recipes` الحالية
- إضافة CLI أو registry
- تحميل تلقائي لأي شيء
- تغيير أي Core code

Titan تضع المعيار. المجتمع يبني. هذا هو الفصل الصحيح.
